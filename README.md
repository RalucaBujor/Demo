# DemoApp

A small SwiftUI app that shows a multi-brand **design system** in practice: one codebase,
three branded apps (**Berry**, **Olive**, **Lime**), all styled from design tokens.

The topics it walks through are on the app's own cards: content injection, behaviors and
styles through modifiers, result builders, previews as documentation, accessibility, and
Sourcery-generated snapshot tests.

## Requirements

- Xcode 26 or newer
- iOS 26.2 or newer (simulator or device)
- Node.js 20+ — only to regenerate the design tokens
- [Sourcery](https://github.com/krzysztofzablocki/Sourcery) — only to regenerate the snapshot tests (`brew install sourcery`)

## Running the app

Open `DemoApp/Demo.xcodeproj` and pick one of the schemes:

| Scheme | App | Bundle ID |
|---|---|---|
| Berry | Berry | `com.ralucabujor.berry` |
| Olive | Olive | `com.ralucabujor.olive` |
| Lime | Lime | `com.ralucabujor.lime` |

All three run the same code. The brand is picked at launch from the bundle ID
(`Brand.current` in `DemoApp.swift`), and every view reads its colors, typography and
spacing from the design tokens in the SwiftUI environment.

## Project structure

```
DemoApp/
├── Demo.xcodeproj
├── DemoApp/                 The app: HomeView, HomeViewModel, sample content
├── DemoAppTests/            Unit tests for HomeViewModel
├── DemoAppUITests/          UI tests for the main flow
└── DesignSystem/            Swift package used by the app
    ├── Sources/DesignSystem/
    │   ├── Components/      DSButton, DSCard, DSTag, DSAlert, DSRatingView, …
    │   ├── Foundation/      Brand, colors, typography, spacing, icons
    │   └── Tokens/Generated/   Swift generated from the JSON tokens — don't edit
    ├── Scripts/             Sourcery template and script for the snapshot tests
    ├── Tests/               Snapshot tests (generated)
    └── tokens-pipeline/     JSON tokens and the Style Dictionary build
```

## Design tokens

Tokens are defined in JSON and turned into Swift with
[Style Dictionary](https://styledictionary.com):

```
tokens-pipeline/tokens/
├── primitives/    raw values per brand (berry.json, olive.json, lime.json)
├── semantics/     what a color means, per brand and light/dark scheme
└── components/    per-component tokens (alert, button, disclaimer, rating)
```

To regenerate the Swift files after changing a token:

```sh
cd DemoApp/DesignSystem/tokens-pipeline
npm ci
npm run build
```

The output lands in `Sources/DesignSystem/Tokens/Generated/`.

## Tests

- **App** — run the tests of the **Berry** scheme (⌘U): unit tests for `HomeViewModel`
  and UI tests for the rating flow. The UI tests find elements by their accessibility
  labels, the same ones VoiceOver and Voice Control use.
- **Design system** — one snapshot test per component preview, generated by Sourcery
  from `Scripts/PreviewProvider.stencil` into `Tests/DesignSystemTests/SnapshotTests.swift`.
  The reference images live in `Tests/DesignSystemTests/__Snapshots__/`.

  Run them on an **iPhone 17 Pro simulator with iOS 26.5** — the one the references were
  recorded on. Other iOS versions render glass, shadows and text slightly differently, so
  there the tests are skipped with a message instead of failing.

  ```sh
  cd DemoApp/DesignSystem
  ./Scripts/sourcery.sh                       # generate tests that verify snapshots
  SNAPSHOT_ACCEPT=1 ./Scripts/sourcery.sh     # generate tests that record new snapshots
  ```

  To update the references after an intended visual change: generate with
  `SNAPSHOT_ACCEPT=1`, run the tests once (they report failures while recording — that's
  expected), then generate again without it and check that they pass. When moving to a new
  iOS version, record again on it and update `referenceOSVersion` in the template.
